| `9.4` | ⑨ 节点准入与生命周期清理 › 节点删除 / 归属转移 → 清跟单关系 | 不留永远不会被分发的脏关系 | node_service.delete_node、users_api.assign_nodes → remove_node_followings | 把跟单节点转移给别的用户后，我的跟单里应不再有它 |
| `9.5` | ⑨ 节点准入与生命周期清理 › 用户删除 → 清其全部跟单关系 | 防止指向已删除用户的脏关系 | users_api.delete_user → follow_service.remove_user_followings | 删除用户后其跟单关系应被级联清掉 |
| `9.6` | ⑨ 节点准入与生命周期清理 › 分组删除 → 级联删跟单行 | 分组没了关系也不能留 | group_service.delete_group 事务内级联 | 带单员删除分组后，跟单员侧不应残留该分组条目 |
| `9.7` | ⑨ 节点准入与生命周期清理 › 带单员切换主节点 | 旧分组不再对外接单，跟单关系保留但收不到新信号 | marketable_reason：分组不含其当前主节点 → 「该带单员已更换主节点，本分组不再对外接单」 | 带单员换主节点后，我的跟单里该分组应标灰并给出原因 |
| `10.1` | ⑩ 权限与审计 › 方向性约定：跟单人人可做 | 能进【带单】菜单即可加入跟单，不需要任何额外能力 | join / leave / me / leaders 只校验 require_menu(MENU_FOLLOW) | 无 follow_leader 的普通用户应能正常跟别人的单 |
| `10.2` | ⑩ 权限与审计 › 方向性约定：带单需能力 | 我能否被别人跟，由我的 follow_leader 能力决定 | permissions.can_be_leader(principal)；能力由管理员在【角色】里授予 | 管理员勾选「带单」能力后该用户才出现在带单列表 |
| `10.3` | ⑩ 权限与审计 › 能力撤销立即生效 | 撤销后立刻从带单列表消失，但存量关系保留、在跑任务跑完 | 按用户名现算 principal（带缓存），避免撤销后仍对外可见 | 撤销能力后刷新列表该用户应消失 |
| `10.4` | ⑩ 权限与审计 › 管理员自动放行 | 管理员天然具备全部能力 | can_capability 内部 is_admin 分支 | 管理员应在带单列表里看到自己 |
| `10.5` | ⑩ 权限与审计 › 不泄露对方分组 | 越权与不存在返回同一个原因 | node_join_reject_reason 不返回「对方分组是否存在」类信息 | 用他人 node_id 探测不应得到可区分的报错 |
| `10.6` | ⑩ 权限与审计 › 审计分类 follow | 加入 / 移出各写一条审计 | persist.audit(category='follow', action='join_follow' / 'leave_follow') | 【操作审计】页按 follow 分类能筛出跟单操作 |
