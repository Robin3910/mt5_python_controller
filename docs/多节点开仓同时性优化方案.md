## 1. 问题描述

**现象**：一条信号触发后，全员同步模式下各节点应当同时开仓，但实际观察到：

- 各节点的**开仓时刻**不一致，有快有慢；
- 各节点的**开仓价**不一致，价差明显。

**需要先明确的一点**：服务端的分发动作**本身已经是并发的**——对所有目标节点用 `asyncio.gather`
一次性下发：

```110:124:backend/app/dispatcher.py
        n = await self._dispatch_sync(signal, signal_id, scope, filters)
        return {"mode": "sync", "targets": n}
...
        targets = await self._eligible_nodes("sync", signal.symbol, filters, signal_id)
        # 并发执行；单个节点异常不影响其它节点
        await asyncio.gather(
            *[
                self.try_open(n, signal, signal_id, scope, filters, wait=False)
                for n in targets
            ],
            return_exceptions=True,
        )
```

所以「不同步」不在服务端分发，而在**命令送达之后、订单进入券商撮合之前**这段路径。
这条路径上每个节点独立走一遍，长度不等、且开仓价是**各节点自己下单那一刻读的自己的 tick**，
服务端从未把价格下发给节点。

> **重要区分**：下文把两个问题分开处理——
> - **时刻不同步**（谁先谁后）→ 方案 A（时间对齐）
> - **价格不同步**（差多少）→ 方案 B（价格锚定）
>
> 方案 A 只能压缩时间差，**不能消除券商之间的报价差异**；后者是固有差异，
> 需要方案 B 才能真正对齐。

## 2. 根因分析

从服务端 `ws.send_json` 到券商撮合，路径如下：

```
服务端                          节点 A                        节点 B
─────────────────────────────────────────────────────────────────────────
send_to_node ─────────────────►  WS 收包
                                  _receiver 串行取消息
                                  _handle → _do_open
                                    └─ _exec(account_info)  ← ① 多余的一次往返
                                       _exec(place_market_order)
                                         └─ symbol_info_tick   ← ② 下单前才读价
                                            order_send
                                  ←── trade_result
```

### 2.1 R1：节点侧 MT5 调用是单线程串行队列（**主因**）

```116:118:node_client/node_client.py
        self._mt5_executor = ThreadPoolExecutor(max_workers=1, thread_name_prefix="mt5")
```

```233:235:node_client/node_client.py
    async def _exec(self, fn, *args):
        """把阻塞式 MT5 调用放到专用单线程执行：不阻塞事件循环，且彼此串行。"""
        return await self.loop.run_in_executor(self._mt5_executor, lambda: fn(*args))
```

单线程是**刻意的正确性设计**（MT5 Python API 非线程安全，见 `node_client/node_client.py` 头部注释），
但代价是所有 MT5 调用排同一条 FIFO 队列。队列上与开仓命令竞争的：

| 竞争者 | 频率 | 单轮 MT5 调用数 | 备注 |
| --- | --- | --- | --- |
| MarketHub 采样 | **每 0.5s** | `positions()` + `orders_get()` + `quotes()` + `symbol_point()` | `quotes` 内部对**每个观察品种**各调一次 `symbol_info_tick` + `symbol_info`，很慢 |
| 账户快照上报 | 每 5s | `positions()` + `orders_get()` + `quotes()` + `account_info()` + `server_time_offset_sec()` | 同样含逐品种报价 |
| 成交历史采集 | 每 60s | `history_deals_get()`（量大） | 券商慢接口，阻塞最久 |
| **开仓命令** | 事件驱动 | 见 R2 | **受害者** |

哪个节点那会儿正在采集 / 采样、券商接口响应多慢，就决定了它多久才轮到 `order_send`。
**这是「有的节点快、有的节点慢」的第一大原因**，且完全是随机的。

### 2.2 R2：开仓命令在真正下单前有额外的 MT5 往返

**normal 链路**——先读一次 `account_info` 只为校验登录号：


**至少 3 次串行排队**，其中 `account_info` 完全可以省掉（登录号是启动时绑定的常量，
`expected_mt5_login` 已在客户端内存里）。

### 2.3 R3：下单前才读 tick，重试会重新读 tick → 价格随时间漂移

```525:548:node_client/mt5_client.py

            # 每次都重新取价（重试时价格可能已变）
            tick = mt5.symbol_info_tick(resolved)
            if not None:
                ...

                ...
                "deviation": self.slippage,
```

关键点：

- `max_retry=3`，瞬时错误（requote 10004 / price changed 10020 / timeout / too many requests）
  会走 `_backoff_sleep(attempt, max_retry)` = `sleep(min(0.3*attempt, 1.5))`，
  累计最多约 **1.8 秒纯睡眠**；
- **每次重试都重新读一次 tick** —— 于是重试越多，下单时刻越晚，价格越偏；
- `deviation=20`（点）本身允许成交价比请求价差 20 个点。

这正好对应「一个节点一次成交（快、价准），另一个节点吃了 requote → 等 0.9s 再打 → 价格已经变了」。

### 2.4 R4：券商之间的 tick 天然不同（固有差异，不可消除）

即使毫秒级完全对齐，两个节点的 XAUUSD ask 也可能差几十美分——不同券商接不同流动性源、
不同做市商报价。**这部分是方案 A 压不下去的**，只有方案 B（锚定同一价位）能对齐。

### 2.5 R5：服务端侧的小偏差（几十毫秒，通常不是主因）

- `all_nodes()` 用 `smembers` + **for 循环逐个 `await get_node`**（N 次串行 Redis RTT）：


- `try_open` 里每个节点串行做 `get_account` → `login_mismatch` → `interval_filter`
  → `position_gate` → `acquire_exec_lock`（Redis `SET NX`）才发命令。
  `asyncio.gather` 只保证「同时进入」，不保证「同时发包」。

### 2.6 R6：服务端的过滤让部分节点「晚很多」或干脆不开

`interval_filter` 用的是节点**上一次上报的快照价**（上报周期 5s，最旧可能是 5 秒前的价）：

各节点用**各自不同时刻的旧价**做区间判定 → 判定结果天然不同，有人被跳过、有人放行。
被放行的节点与被跳过的节点之间，开仓时刻相差可能长达数秒。

### 2.7 R7：节点端 WS 命令是串行处理的


`_do_strategy_start` 也是内联。一个节点上排在开仓命令后面的任何命令都要等这一单彻底返回。

### 2.8 根因汇总

| 编号 | 根因 | 影响维度 | 量级估计 |
| --- | --- | --- | --- |
| R1 | MT5 单线程 FIFO 队列被采样/快照/成交采集抢占 | 时刻 | 100ms ~ 数秒（随机） |
| R2 | 下单前的多余 MT5 往返（`account_info` / `symbol_spec` / `quotes`） | 时刻 | 每跳 10~200ms，累加 |
| R3 | 重试退避 sleep + 每次重试重读 tick | **时刻 + 价格** | 0.3 ~ 1.8s + 同期价格漂移 |
| R4 | 券商报价差异 | 价格 | 固有，不可消除 |
| R5 | 服务端逐节点串行取数 / 发包 | 时刻 | 数十 ms |
| R6 | 区间过滤用旧快照价，节点间判定不一致 | 时刻（跳过/放行差异） | 数秒 |
| R7 | 节点端命令串行处理 | 时刻 | 视队列长度 |

## 3. 目标与量化指标

| 编号 | 指标 | 现状（待实测确认） | 目标 |
| --- | --- | --- | --- |
| G1 | 节点间**下单时刻**极差（max−min） | 待测（预估 0.3 ~ 数秒） | **< 100ms** |
| G2 | 节点间**开仓价**极差（市价单） | 待测（预估数十点 ~ 数百点） | 压到 R4 券商差异量级（方案 B 达成同价） |
| G3 | 节点间**开仓价**极差（strategy 限价开仓） | 本已同价（挂单价来自信号） | 保持不变（回归保护） |
| G4 | 开仓失败率 | 待测 | 不上升 |
| G5 | 端到端（信号 → 成交）延迟 P95 | 待测 | 不劣化 |

> **G2 的诚实说明**：在「各节点各自市价下单」的前提下，**价格极差的下界就是 R4（券商报价差异）**，
> 方案 A 只能消除「因为晚打了几秒而多出来的」那部分。想真正同价，必须走方案 B。

## 4. 方案总览

```
                    ┌──────────────── 方案 A：时间对齐 ────────────────┐
信号 ──► 服务端 ──►│ 并发下发 ──► 节点插队 ──► 省掉前置往返 ──► 首轮不睡 │
                    └──────────────────────────────────────────────────┘
                                        │
                    ┌──────────────── 方案 B：价格锚定（可选） ─────────┐
                    │ 服务端取参考价 P ──► 各节点挂 P 的限价单（可选兜底市价） │
                    └──────────────────────────────────────────────────┘
```

| 编号 | 改造项 | 类别 | 风险 | 收益 | 阶段 |
| --- | --- | --- | --- | --- | --- |
| **M1** | 节点侧 MT5 调用**优先级队列**（开仓命令插队） | A | 中 | **高** | 一期 |
| **M2** | 开仓路径去掉下单前的 `account_info` 校验往返 | A | 低 | 中 | 一期 |
| **M3** | 市价单**首轮不 sleep** + 失败快速重试 | A | 低 | **高** | 一期 |
| **M4** | strategy 首单前置的 `symbol_spec` / `quotes` **复用 hub 缓存** | A | 低 | 中 | 一期 |
| **M5** | 服务端 `all_nodes` / 发包**并行化** | A | 低 | 低 | 一期 |
| **M6** | 命令携带**参考价 + 时间戳**，节点按参考价锚定 | B | 中 | **高** | 二期 |
| **M7** | 区间过滤改用**节点实时报价**而非 5s 旧快照 | A | 中 | 中 | 二期 |
| **M8** | 全链路**时延埋点**（发包/收包/下单/成交 四个时间戳） | 观测 | 无 | 高（前置） | **零期** |

## 5. 改造项详述

### M8（全链路时延埋点）— 零期，优先

**目的**：把「慢在哪一段」变成可测量数据。

**改动点**

1. 服务端 `signal_dispatch` 新增列 `sent_at`（下发时刻）。
   复用现有 `dispatched_at`（`record_dispatch` 落库时刻）也可以，但它在 `send_to_node` **之后**，
   语义不够准。新增一列更清晰。

   ```226:236:backend/app/orm.py
       decided_vol: Mapped[float | None] = mapped_column(Float, nullable=True)  # 实际决策手数
       ...
       dispatched_at: Mapped[datetime | None] = mapped_column(DateTime, nullable=True)
       finished_at: Mapped[datetime | None] = mapped_column(DateTime, nullable=True)
   ```

   → `backend/app/db.py` 补一个 `_migrate_dispatch_sent_at_column`（与
   `_migrate_dispatch_price_column` 同款写法，`create_all` 不改已存在的表，必须显式 ALTER）。

2. 节点端 `trade_result` 回报增加三个**相对时刻**（用节点本地 `time.time()`，
   服务端收到后再换算，避免跨机时钟偏差）：

   | 字段 | 含义 |
   | --- | --- |
   | `recv_at` | 节点从 WS 读到这条命令的时刻 |
   | `order_at` | 调 `mt5.order_send` 之前的时刻 |
   | `filled_at` | `order_send` 返回（拿到成交价）的时刻 |

   节点已在 `res` 里回传 `price`（成交价），服务端 `update_dispatch_result` 已经落库到
   `signal_dispatch.price`：


   → 把 `recv_at` / `order_at` 也写进 `signal_dispatch`（或先只写进 `error`/扩展 JSON 字段做灰度）。

3. **分析口径**：按 `signal_id` 查同一批
   `finished_at - sent_at`（服务端视角总耗时）、
   `order_at - recv_at`（节点排队耗时 → 反映 R1/R2）、
   `filled_at - order_at`（券商往返耗时 → 反映 R3/R4）、
   以及 `price` 的极差。

**验收**：能对任意一条历史信号打印出上述四段分解。

| `frontend/src/views/EventsView.vue` / `NodeDetailView.vue` / `GroupSignalsView.vue` | 展示「节点排队」「券商往返」两列 |

**两个重要的口径决定**

1. **跨机时钟不可比**。节点上报的 `recv_at` / `order_at` / `filled_at` 用的是节点本地时钟，
   与服务端时钟不同源。因此：
   - 跨节点比较**一律走服务端时间轴**（`sent_at` → 服务端收到回报的时刻）；
   - 同节点内的差值（`queued_ms` / `order_to_fill_ms`）才是可直接解读的指标；
   - API **不暴露** `recv_at` 等绝对时刻给前端做跨节点相减（会误导）。

2. **内部键不进协议**。MT5 客户端返回的 `_order_at` / `_filled_at` 是内部观测键，
   在 `node_client` 层就被 `pop` 掉并换算成 `queued_ms` / `order_to_fill_ms`，
   不会出现在 `trade_result` 的 data 里。

### M1（MT5 优先级队列，开仓插队）— 一期

**问题**：R1。开仓命令排在 FIFO 队尾，可能被一轮 `history_deals_get`（60s 一次，量大）
或某次 15 个品种的 `quotes()` 挡在后面。

**方案**：把单线程执行器换成**带优先级的串行执行器**——仍然保证「同一时刻只有一路在操作终端」
（MT5 线程安全的硬要求不变），但让高优先级任务插到队首。

**实现要点**

- 新增 `node_client/mt5_queue.py`：

  ```python
  class PriorityMT5Executor:
      """单线程 + 优先级的串行执行器。

      MT5 Python API 非线程安全，必须同一时刻只有一路在操作终端；
      但优先级让「开仓」插到「采样/采集」前面。
      """
      def __init__(self, name: str = "mt5"):
          ...
      async def submit(self, fn, *args, priority: int = 0) -> Any: ...
      def submit_low(self, fn, *args) -> Any: ...   # 采样 / 快照 / 采集
  ```

- 优先级约定（数值越大越优先）：

  | 优先级 | 用途 | 调用点 |
  | --- | --- | --- |
  | 100 | 开仓（`place_market_order` / `place_pending_order`） | `_do_open`、`_open_first`、`_risk_send_order` |
  | 90 | 平仓（`close_*`）——平仓失败比开仓延迟更危险 | `_close_all`、`_do_close` |
  | 50 | 撤销挂单 | `_cancel_counter_orders` 等 |
  | 0 | 账户快照 / 成交采集 / 行情探针 | `_snapshot`、`_collect_deals`、`_do_market_probe` |
  | -10 | MarketHub 采样 | `market_hub.py` 的 `_exec` |

- 底层实现建议：**一个 worker 线程 + 一个 `PriorityQueue`**，而不是「多个线程抢锁」。
  单线程保证 MT5 安全，`PriorityQueue` 保证插队语义，且能保留 FIFO 兜底（同优先级内 FIFO）。

- **插队不能破坏的语义**：正在执行中的 MT5 调用**不可中断**（MT5 调用本身是同步的）。
  插队只影响「还没开始执行」的队列内容。这是物理上限——
  如果插队时恰好有一轮 `quotes()` 正在跑（可能几十 ms~数百 ms），插队也救不了。
  → 因此 M4（复用缓存）与 M8（埋点）必须配合 M1 一起做。

**风险**

| 风险 | 缓解 |
| --- | --- |
| 采样被持续插队的开仓饿死 | 采样是**周期**任务，不依赖事件到达；且给采样一个「最大等待」上限（超过 N 秒就提升优先级），或保留一个「低优先级任务最多连续等待 K 拍」的提升规则 |
| 账户快照长期不更新 → 服务端区间过滤用旧价 | 快照优先级设为 0（高于采样），并在插队饥饿时提升；或对快照单独限频 |
| 复杂度上升 | 抽成独立模块 + 独立单测；`NodeClient._exec` 保持签名不变（默认优先级 0），只在关键路径显式传高优先级 |

**替代方案（更简单，先评估）**：不引入优先级队列，改为**开仓前临时挂起采样**。
例如 `_do_open` 设置一个 `self._priority_open_at` 时间戳，`market_hub` 的采样循环检测到
「距上次开仓不足 N 秒」就跳过本轮采样。实现量远小于优先级队列，但牺牲采样连续性。
→ **待确认走哪条路**（见 §12）。

### M3（市价单首轮不 sleep + 快速重试）— 一期

**问题**：R3。`place_market_order` 现在的重试策略：

```525:576:node_client/mt5_client.py
        while attempt <= max_retry and fill_idx < len(fillings):
            # 每次都重新取价（重试时价格可能已变）
            tick = mt5.symbol_info_tick(resolved)
            ...
            rc = result.retcode
            if rc in (RET_DONE, RET_DONE_PARTIAL):
                ...
            if rc == RET_INVALID_FILL:
                fill_idx += 1  # 换下一种填充模式（不消耗重试次数）
                continue
            if rc in TRANSIENT:
                # 瞬时错误：退避后重试（下一轮会刷新价格）
                attempt += 1
                _backoff_sleep(attempt, max_retry)
                continue
```

现状问题：
1. **首轮就可能 sleep**：`max_retry=3`，第一次失败 `attempt=1` → `sleep(0.3)`。
2. 每次重试**重新读 tick** → 价格漂移。
3. 累计最多约 1.8s 纯睡眠。

**方案（对齐 §18.20「爆发式首轮」思路）**

- **首轮 `max_retry=0`**：失败**不 sleep**，立刻换下一个填充模式再试
  （`RET_INVALID_FILL` 本来就不消耗重试次数，直接换模式即可）；
- **第二轮起才带退避**：此时才 sleep 0.3s / 0.6s / 0.9s；
- **重试时固定价格**：第一次读的 tick 固定下来，重试用**同一个 `price`** 再试
  （`deviation` 已容忍 20 点），避免价格漂移。
  → 代价：若价格真变了，重试可能全部失败。折中：**只固定第一次重试的价格，
  第二次起重新读 tick**。

  ```python
  # 伪代码
  first_tick = read_tick()
  price = first_tick.ask if action == "BUY" else first_tick.bid
  for attempt in range(...):
      if attempt >= 1:                 # 第二轮起才刷新价
          price = read_tick()...
      result = order_send(price, ...)
      if ok: return
      if invalid_fill: fill_idx += 1; continue   # 不 sleep
      if transient:
          if attempt == 0: continue    # 首轮不睡
          backoff_sleep(attempt)
  ```

- **平仓路径同样处理**：`close_position` 有一份几乎相同的循环，建议抽出公共实现
  （`close_position` 的失败后果比开仓更严重，不能照搬「快速失败」策略，只统一「首轮不睡」）。

**风险**

| 风险 | 缓解 |
| --- | --- |
| 无 sleep 的重试可能在行情剧烈时全部失败 | 只把「首轮」改成不睡；后续退避不变 |
| 固定价格后被拒 | `deviation` 20 点通常够；第 2 轮起恢复重新读价 |
| 券商返回 `RET_INVALID_FILL` 频繁 | 已在 `filling_modes` 里备好了 3 种填充模式，不消耗重试次数 |

**回归要点**：`node_client/test_mt5_connect.py` / mock 的 `place_market_order` 行为需保持一致。

### M4（strategy 首单前置调用复用缓存）— 一期

**问题**：R2 在 strategy 链路的体现。

`_open_first` 下单前要 `_stops_on_open` → `_manual_symbol_spec()` + `_open_quote()` + `_read_balance()`。

**方案**

| 前置调用 | 现状 | 方案 |
| --- | --- | --- |
| `symbol_spec()` | `_risk_symbol_spec` 已缓存（任务期内合约规格不变），但 `_manual_symbol_spec` **没缓存** | 统一走一个任务级缓存（`_symbol_spec_cache`），两条路径共用 |
| `quotes()` | `_open_quote()` 单独再读一次报价 | 复用 **MarketHub 最近一轮采样**的报价（hub 每 0.5s 已经在读 `quotes`） |
| `account_info()`（余额） | 每次读 | 复用最近一次账户快照里的 `balance`（`_reporter` 5s 一轮） |

**关键点**：hub 的报价缓存已经存在——`MarketHub._read_quotes` 每轮读一次，
`_pick_price` 从中取值。只需把这一轮的报价暴露给 runner 用（例如 hub 上挂一个
`last_quotes` 快照，`_open_quote` 优先取它，miss 时才自己读）。

**收益**：strategy 链路首单从 3~5 次 MT5 往返降到 1 次（`order_send`）。

**风险**

| 风险 | 缓解 |
| --- | --- |
| hub 报价比实际下单时刻旧（最多 0.5s） | 开仓价仍以 `order_send` 内部自读 tick 为准；hub 报价只用于**计算止损止盈 / 预估手数** |
| 止损距离用旧价算 → 实际风险偏离 | 以损定量的手数是按止损距离反推的，0.5s 的价差通常远小于止损距离；必要时保留「算手数时用实时价」的兜底 |
| hub 未启动 / 该品种未被订阅 | `_open_quote` 保留自己读报价的 fallback |

**注意**：`hold_when_empty` 的网格任务、`limit_entry` 的限价任务，报价用途不同，
需逐条确认哪些路径可以换成 hub 缓存。

### M7（区间过滤改用节点实时报价）— 二期

**问题**：R6。各节点用**各自 5s 前的旧快照价**做区间判定，导致判定结果不一致，
有人被跳过、有人放行，放行与跳过之间相差数秒。

**方案**

- 服务端在判定前，向目标节点索取一次**实时报价**（复用 `market_probe` 的 RPC + 缓存），
  用它替代 `rules.pick_price` 的快照价；
- 或者：节点侧在 `account` 快照之外，**提高报价上报频率**（`account_report_interval` 已支持小数，
  下限 0.05s，见 `node_client/config.py` 的 `clamp_account_report_interval`）。

**风险**

| 风险 | 缓解 |
| --- | --- |
| 提高上报频率 → 节点 MT5 队列压力上升 → **反而拖慢开仓**（与 M1 冲突） | 优先走「按需 RPC 取价」而不是「提高全量上报频率」 |
| 取价 RPC 超时 → 判定无价 → 被拦 | 超时后回退到快照价（现状行为） |

**与 M1 的优先级关系**：M1 让开仓插队，M7 的 RPC 取价是「判定阶段」的事，
发生在发包之前，不进入节点的 MT5 队列——两者不冲突。

## 11. 风险、边界与明确不做的事

### 11.1 明确不做的事

| 不做 | 原因 |
| --- | --- |
| 多线程并行 `order_send` | MT5 Python API 非线程安全，会串 `last_error`、与策略监控抢同一批仓、更易吃 10024。§18.20 已明确此结论 |
| 引入 MQL5 EA 做 `OrderSendAsync` | 需要额外部署与版本对齐，本次不做（可作为长期方向） |
| 把 MT5 队列改成多线程 + 锁 | 同上，非线程安全 |
| 用「信号时刻的服务器报价」直接当成交价 | 服务端没有券商实时价，只能取参考节点的报价，精度受限于参考节点 |
| 保证「所有节点绝对同价」 | 券商报价差异（R4）是固有差异，方案 B 也只在「限价路径 + P 可达」时成立 |

### 11.2 主要风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 优先级队列改造引入并发 bug | 节点侧交易逻辑异常 | 抽成独立模块 + 完整单测；`.env` 开关可一键退回 |
| 插队导致采样/快照饿死 | 服务端区间过滤用陈旧价；策略监控延迟 | 采样是周期任务不依赖事件；给低优先级任务设最大等待上限 |
| 首轮不 sleep 放大券商压力 | 可能触发 `TOO_MANY_REQUESTS` | 只对「开仓首轮」放开；券商限流由 `TRANSIENT` 集合统一处理 |
| M6 限价单挂不上 | 仓位建不起来 | 保留市价兜底 + `degraded` 标记 + 后台可见 |
| 协议字段增加 | 旧节点 / 新服务端混跑 | 全部字段可选，旧节点忽略；灰度期内新旧并存没问题 |

### 11.3 边界

- **网格策略（`tpl_3`）** 的「等触发价再建仓」**不属于缺陷**——各节点触发时刻天然不同，
  本方案不改变网格语义；
- **poll 轮询模式** 本来就是「一个节点开仓」，不涉及同时性问题；
- **strategy 限价开仓** 已是同价（G3），本方案只做回归保护。

## 12. 待确认事项

> **以下问题需要你确认后，我才开始动代码。**

### Q1：M1 走「优先级队列」还是「开仓时挂起采样」的简化版？

- **A. 优先级队列**（`node_client/mt5_queue.py`）：彻底，但改动面大、需处理饥饿；
- **B. 简化版**：开仓命令到达时，MarketHub 采样循环跳过接下来 N 秒的采样。改动小，
  但会丢采样连续性（网格策略依赖采样连续性，**风险不低**）。

→ 我倾向 **A**，因为 B 会直接伤害网格策略。

### Q2：M6（参考价锚定）要不要做？它有一个明确的取舍

限价对齐 = **价格严格一致**，但**成交时刻反而更分散**（要等价格碰到 P）。
市价对齐 = **时刻尽量一致**，但**价格受券商差异限制**。

→ 需要你明确：**业务上更看重「同价」还是「同刻」？**
→ 如果业务主要走 strategy 限价链路（已同价），M6 可以直接不做。

### Q3：M3 的「第一次重试沿用首次价格」要不要开？

固定价格 → 价格更一致，但若价格真变了可能重试全败。
→ 我倾向**只固定第一次重试**，第二次起恢复重新读价。

### Q4：M7（实时报价做区间过滤）是否必要？

它解决的是「各节点判定结果不一致、有的被跳过」。
→ 如果业务上「某些节点该被跳过」是正常现象（本来就在预期内），M7 的收益不大，
可以推迟到二期再看。

### Q5：是否接受「服务端下发后到券商撮合」的最坏延迟无法压到 50ms 以内？

物理上限在于：插队时若恰好有一轮 15 品种 `quotes()` 正在跑，这段时间无法中断。
→ 若要进一步压，需要**削减单轮采样的品种数**（只采样策略任务涉及的品种 + 观察列表），
这是一条独立的优化线。

### Q6：改动范围确认

- 是否允许改 `node_client/mt5_client.py` 的 `place_market_order` / `close_position` 重试语义？
  （涉及已有行为变更，需要 `test_mt5_connect.py` 等回归）
- 是否允许新增 `signal_dispatch` 的列（需要 ALTER 迁移）？

> **注意**：strategy 链路的同类数据在 `group_task_dispatch` 表，列名完全一致，
> 可用同样的 SQL 口径查。

**一条直接可用的基线查询**（找出排队最久的节点，验证 M1 的收益）：

```sql
SELECT node_id,
       COUNT(*) AS n,
       ROUND(AVG(queued_ms), 1)       AS avg_queued_ms,
       ROUND(MAX(queued_ms), 1)       AS max_queued_ms,
       ROUND(AVG(order_to_fill_ms), 1) AS avg_fill_ms
FROM signal_dispatch
WHERE queued_ms IS NOT NULL
GROUP BY node_id
ORDER BY avg_queued_ms DESC;
```

**找价差最大的信号**（验证 M6 的必要性）：

```sql
SELECT signal_id,
       COUNT(*) AS nodes,
       ROUND(MAX(price) - MIN(price), 6) AS price_spread,
       ROUND((MAX(finished_at) - MIN(finished_at)) * 1000, 1) AS time_spread_ms
FROM signal_dispatch
WHERE price IS NOT NULL AND status = 'done'
GROUP BY signal_id
HAVING nodes > 1
ORDER BY price_spread DESC
LIMIT 20;
```
