# 软件需求评估与报价框架

> **适用项目**：`mt5_python_controller`（MT5 多节点交易管控平台）
> **文档定位**：本文件是**方法论与模板**。接到具体需求后，产出《需求评估表》+《报价单》，格式见 §9。
> **版本**：v2.1 ｜ **建立日期**：2026-10-27 ｜ **上次修订**：2026-10-27
>
> ### 修订说明（重要）
>
> v1.0 的估算模型是**按"无 AI 团队 + 传统人天费率"**建立的，在 AI 辅助开发场景下**系统性高估 5~9 倍**。
> 实测反例：《实时盈亏归因看板》v1.0 估 20.5 人天 / 报价 9.5 万（未税），
> 实际 AI 辅助下 **1~2 人天**即可完成（但**测试用例未覆盖完整**）。
>
> v2.0 换掉了估算模型；v2.1 修正了 v2.0 自身的两处算术/建模错误。
>
> **v2.0 的根本改动**：
>
> | # | v1.0 做法 | v2.0+ 做法 | 影响 |
> |---|---|---|---|
> | 1 | 单一"人天"计量 | **三层时间模型**：产出人天 / 物理工期 / 覆盖度预算（§3） | 概念层修正 |
> | 2 | 工时按传统估算 | **任务类型 × 基础人天 × AI 压缩系数**（§4） | 产出人天降 5~9x |
> | 3 | 工期 = 人天 ÷ 并行数 | **工期 = max(产出链) + 物理下限**（§5） | 工期只降 1.5~2x |
> | 4 | 测试作为开发附属 | **覆盖度分级 C1/C2/C3 + 范围分级 S1/S2/S3**（§6） | 客户可选档 |
> | 5 | 人天 × 日费率 | **四段式成本**：判断 / 产出 / 验证 / 保障（§7.2） | 报价降 4~6x |
> | 6 | 单点报价 | **三档套餐菜单 + 价格地板**（§7.5） | 拒绝不经济的单 |
>
> **v2.1 修正的两处 v2.0 错误**（均由算术校验发现）：
>
> | # | v2.0 的错误 | 后果 | v2.1 修正 |
> |---|---|---|---|
> | 1 | **漏算**测试执行工时（T12/T13 示例中 3.15 人天 QA 未进任何成本桶） | 报价与 L1 人天对不上，报价看起来"凭空来的" | **四段式**把验证投入独立成段（§7.2） |
> | 2 | **重复计算**——AI 产出人天既乘角色日费率、又单列一份"监督摊销" | 成本虚高 20~30% | 监督工时已含在 ② 中，AI 工具摊销只计 Token/许可 |
>
> **v2.1 另增两项**：
> - **范围分级 S1/S2/S3**（§6.2）——与覆盖度 C1/C2/C3 成对出现，避免"缩水功能 + 高覆盖"或"完整功能 + 没验证"两类争议
> - **示例数字全部由脚本生成**（`scripts/_calc_example.py`）——文档内部自洽，改任务清单即可刷新
>
> **当前 P2 档报价**：L1 6.23 人天 / 工期 10 日历日 / **未税 3.35 万 / 含税 3.55 万**
> （v1.0 为 20.5 人天 / 29 日历日 / 9.5 万未税）

## 0. 使用方式

本文档回答三个问题：**这个需求要花多久？需要多少钱？依据是什么？**

```
① 读需求 → ② 拆 WBS（标注任务类型）→ ③ 套 AI 压缩系数算产出人天
        → ④ 叠加物理工期下限得日历工期 → ⑤ 选覆盖度档位 C1/C2/C3
        → ⑥ 选交付范围 S1/S2/S3 → ⑦ 四段式成本测算 → ⑧ 套毛利率出报价 → ⑨ 附边界条件
```

**四条铁律（v2.1）：**

1. **先拆后估**——不拆 WBS 不给数。每条估算须可追溯到具体代码文件或需求条目。
2. **产出人天 ≠ 工期 ≠ 报价**——三者量级完全不同，**必须分开报**。混为一谈是 v1.0 最大的错误。
3. **范围与覆盖度成对报**——S1/S2/S3 与 C1/C2/C3 必须同时出现，否则必然扯皮。
4. **L1 人天必须在成本模型里恰好出现一次**——漏算和重复计算是报价失真的两大来源（v2.1 的两处修正都是这类）。

> **贯穿全文的方法论纪律**：任何新增的估算维度，都必须先问
> **"AI 能不能压缩它？压缩后谁承担剩余风险？"** —— 回答不了这个问题，就不要放进成本模型。

## 1. 核心认知：AI 改变了什么，没改变什么

这是整个 v2.0 框架的地基。**不先想清楚这一点，所有数字都会系统性偏一个方向。**

### 1.1 被 AI 压缩的 vs 压不动的

| 环节 | AI 效果 | 原因 |
|---|---|---|
| 样板代码、CRUD、字段透传 | **压缩 8~12x** | 模式明确，AI 强项 |
| 已知范式的业务逻辑 | 压缩 4~6x | 有参考实现 |
| 单元测试编写 | 压缩 5~8x | 用例能生成，但**覆盖度≠用例数**（见 §1.3） |
| 自动化回归执行 | 压缩 2~3x | 脚本写好后机器跑，人只审结果 |
| UI 拼装、图表、样式 | 压缩 5~8x | |
| 文档、交付物 | 压缩 4~6x | |
| **跨端协议/契约对齐** | 压缩 3~4x | 需人工对齐语义 |
| **调试、疑难攻坚、性能调优** | 压缩 1.5~2x | AI 帮不上忙 |
| **需求澄清、方案决策、验收** | **压缩 ~1x** | 人的本质工作，AI 无法替代判断 |
| **用例设计（定义边界）** | 压缩 2~3x | AI 能写用例，写不出"该测什么" |
| **测试结论判断（够不够）** | **压缩 ~1x** | 机器能跑，不能判定"够不够" |
| **影子运行、灰度放量** | **压缩 0x** | **物理时间，AI 无能为力** |
| **需求方响应、决策周期** | **压缩 0x** | 组织时间 |

### 1.2 关键结论一：产出人天降 9x，工期只降 1.8x

以《实时盈亏归因看板》实测为例：

```
v1.0 预估：  产出 20.5 人天 → 工期 4.1 周
v2.0 实测：  产出  1.8 人天 → 工期 4~5 个日历日（档位 A）
                  ↓ 8.7x              ↓ 仅 4.5x（含 1~3 日需求确认物理下限）
```

**为什么工期压缩不了那么多？** 因为工期里有大量 AI 压不动的成分：

- 需求方书面确认：**1~3 个日历日**（人的决策周期）
- 实盘观察、灰度放量：**3~10 个日历日**（物理时间）
- 跨端联调、部署窗口：**0.5~1 个日历日**

> **报价启示**：人天和工期不能同比例降，**所以报价也不能同比例降**。v1.0 的 9.5 万如果直接除以 9 变成 1 万，就等于连"验证覆盖度"和"责任兜底"的钱都没了——那不是降价，是把风险转嫁给客户，最终会在实盘事故里加倍还回去。

### 1.3 关键结论二：AI 压缩"产出速度"，不压缩"验证覆盖度"

这是你反馈里那句"**没能覆盖全测试用例**"揭示的关键机制：

| 概念 | 含义 | AI 的影响 |
|---|---|---|
| **用例数量** | 写出来多少条 | 压缩 5~8x（AI 写得快） |
| **覆盖完整度** | 该测的场景是否都被测到 | **压缩 ~1x**（"该测什么"是定义问题，不是生成问题） |
| **验证结论可信度** | 测完能否确信功能正确 | **压缩 ~1x**（影子运行、故障注入、极端行情都需物理时间） |

**推论**：AI 时代真正的稀缺资源**从"写代码的能力"转移到了"定义验证边界的能力"**。这直接决定了两件事：

1. **测试工作量不能按压缩系数打折**——甚至在 AI 辅助下，**测试的相对占比会上升**（因为开发变便宜了）
2. **报价必须绑定覆盖度档位**——客户买的是覆盖度，不是代码行数

### 1.4 关键结论三：价值上移是必然的

| 传统时代赚钱靠 | AI 时代 |
|---|---|
| 编码工时 | **领域判断**（知道"盈亏归因"该怎么归、MT5 数据的坑在哪） |
| 人力规模 | **责任承担**（出问题的兜底） |
| 交付代码 | **集成与运维**（让 100 个节点稳定跑起来） |

如果一家公司还在按"人天 × 费率"卖编码工时，**这个商业模式正在被淘汰**。v2.0 框架的费率结构（§7.1）刻意让**判断类单价高于执行类**，就是在引导这个转向。

## 3. 三层时间模型（核心）

**必须分开报、分开估算、分开呈现的三个量。**

```
┌──────────────────────────────────────────────────────────────────┐
│  L1  产出人天 (Output Effort)                                     │
│      = Σ(任务类型基础人天 × AI 压缩系数)                          │
│      性质：可被 AI 压缩 5~9x    用途：成本测算、资源排布          │
├──────────────────────────────────────────────────────────────────┤
│  L2  物理工期 (Elapsed Calendar)                                 │
│      = max(各阶段产出链) + Σ(物理下限：确认/联调/灰度/上线)        │
│      性质：部分可压缩（≈1.5~2x） 用途：客户承诺的交付日期          │
├──────────────────────────────────────────────────────────────────┤
│  L3  覆盖度预算 (Coverage Budget)                                 │
│      = 档位(C1/C2/C3) → 用例集 + 验证手段 + 物理观察期             │
│      性质：几乎不可压缩          用途：报价的核心杠杆             │
└──────────────────────────────────────────────────────────────────┘
```

### 3.1 L1 产出人天

```
产出人天 = Σ_i ( 基础人天_i × AI压缩系数_i )
```

**基础人天**：按"无 AI、熟练工程师"的工时估算——这是**标准工作量**（Standard Effort），不是最终投入。
**AI 压缩系数**：查 §4 系数表，按任务类型取值。

> ⚠️ **不要把系数乘到工期上**。系数只作用于 L1。

### 3.2 L2 物理工期

```
物理工期 = max( 沟通链, 开发链, 测试链 )  +  强制串行节点
```

**强制串行节点（不可并行、不可压缩）**：

| 节点 | 下限 | 原因 |
|---|---|---|
| 需求方书面确认 | 1~3 日历日 | 组织决策 |
| 跨端联调窗口 | 0.5~1 日历日 | 需两端同时在线 |
| 影子运行（若选 C3） | 1~3 日历日 | 需真实数据积累 |
| 灰度放量（若选 C3） | 1~2 日历日 | 小流量验证 |
| 生产上线窗口 | 0.5~1 日历日 | 通常非工作时段 |

**下限校验规则**：若算出的物理工期 < 各阶段物理下限之和，则**取下限**，不因 AI 快而缩短承诺。这条规则防止过度承诺。

### 3.3 L3 覆盖度预算

见 §6。覆盖度是**客户与开发者之间最重要的契约**——它把"做完了"这个模糊状态变成可验收的具体清单。

## 4. AI 压缩系数表

**用法**：估出基础人天 → 查任务类型 → 乘系数 → 累加得产出人天。

| 任务类型 | 系数 | 典型基础人天 | 产出人天 | 说明 |
|---|---|---|---|---|
| **T1 样板 CRUD / 字段透传** | **0.10** | 0.5~1.0 | 0.05~0.10 | 模型、序列化、路由、增删改查 |
| **T2 已知范式的业务逻辑** | **0.15** | 1.0~3.0 | 0.15~0.45 | 有参考实现可循。**若属模型强项域（标准 Web 栈、常见图表、常规聚合），按 0.10 取** |
| **T3 UI 拼装 / 图表 / 样式** | **0.15** | 0.5~2.0 | 0.08~0.30 | Element Plus + ECharts 组合 |
| **T4 单元测试编写** | **0.15** | 0.5~1.5 | 0.08~0.23 | ⚠️ 只压"写"，不压"覆盖" |
| **T4b 自动化回归脚本编写** | **0.12** | 0.5~1.5 | 0.06~0.18 | 脚本写好后由 CI 执行，人只审结果 |
| **T5 跨端协议 / 契约对齐** | **0.30** | 1.0~2.0 | 0.3~0.6 | 三端（后端/节点/前端）语义对齐 |
| **T6 文档 / 交付物** | **0.20** | 0.5~1.5 | 0.1~0.3 | |
| **T7 数据模型变更 + 迁移** | **0.30** | 1.0~3.0 | 0.3~0.9 | 迁移脚本 + 对账 |
| **T8 调试 / 疑难攻坚** | **0.60** | 1.0~5.0 | 0.6~3.0 | AI 帮不上忙，占比越大事项越慢 |
| **T9 性能 / 并发 / 稳定性调优** | **0.60** | 1.0~4.0 | 0.6~2.4 | |
| **T10 需求澄清 / 方案决策** | **1.00** | 0.3~1.0 | 0.3~1.0 | **人的工作，不打折**。基础人天下限已按“AI 辅助整理纪要/出草案”下调 |
| **T11 用例设计（定义边界）** | **0.50** | 0.3~1.0 | 0.15~0.50 | AI 能写用例，写不出“该测什么” |
| **T12 人工执行验证** | **0.60** | 0.5~2.0 | 0.3~1.2 | ⚠️ 非 1.0！CI 跑脚本后，人只审结果与异常 |
| **T13 影子运行 / 灰度观察** | **1.00** | 0.5~2.0 | 0.5~2.0 | **纯物理时间** |
| **T14 实盘资金相关逻辑** | **0.70** | 2.0~8.0 | 1.4~5.6 | 系数偏高：需反复验证与回滚设计 |
| **T15 部署 / 环境 / 打包** | **0.40** | 0.5~2.0 | 0.2~0.8 | |

### 4.1 系数校准指引

| 情形 | 系数调整 |
|---|---|
| 项目中**已有同类实现**可参考 | 系数 × 0.8（有样板可抄） |
| 需要**从零设计**无先例 | 系数 × 1.3（AI 无参照物） |
| 团队已熟练使用 AI + 有项目级规则文件 | 全部系数 × 0.85 |
| 需求描述含糊、需大量澄清 | T10/T11 系数 × 1.5 |
| 涉及实盘资金 | T14 系数 × 1.2，且强制 C3 档 |

### 4.2 系数取值纪律

- **只取表内值，不自创**。自创系数是估算失控的第一入口。
- **每 3 个需求回填一次实测**——记录"预估产出人天"vs"实际投入人天"，滚动修正本表。
- **T8/T9/T13/T14 是关键路径风险点**——这些系数接近 1，是工期承诺最容易失守的地方。排期时给它们单独留缓冲。

## 5. 物理工期下限表

| 阶段 | 绝对下限（日历日） | 说明 |
|---|---|---|
| 需求澄清与书面确认 | **1**（常规 2~3） | 需求方内部决策时间 |
| 技术方案 | 0.5 | 可与澄清部分重叠 |
| 开发（≤2 人天产出时） | 0.5 | AI 时代的"一下午"场景 |
| 开发（2~8 人天产出时） | 1~3 | |
| 开发（>8 人天产出时） | 3~8 | |
| 联调 | 0.5~1 | 跨端 |
| 测试执行（C1） | 0.5 | |
| 测试执行（C2） | 1~2 | |
| 影子运行 + 灰度（C3） | 3~7 | **物理时间，不可压缩** |
| 生产上线 | 0.5~1 | |

**推导出的常见档位工期**：

| 需求规模 | C1 档工期 | C2 档工期 | C3 档工期 |
|---|---|---|---|
| 小型（产出 ≤2 人天） | **4~5 日历日** | 5~7 日历日 | 10~14 日历日 |
| 中型（产出 2~6 人天） | 6~9 日历日 | 8~12 日历日 | 14~20 日历日 |
| 中大型（产出 6~15 人天） | 10~15 日历日 | 12~18 日历日 | 18~28 日历日 |
| 大型（产出 >15 人天） | 15~22 日历日 | 18~26 日历日 | 25~40 日历日 |

> **对比传统估算的 4~7 周**：AI 辅助下小型需求**一周内可交付**。这是 AI 带来的真实收益，**必须让客户看到**——这是说服客户接受低报价的最有力论据，也是你与小团队竞争的唯一优势。

## 6. 交付套餐体系（范围的杠杆 × 覆盖度的杠杆）

**报价要同时锚定两个维度，缺一个就会失真：**

| 维度 | 问的问题 | 杠杆 |
|---|---|---|
| **覆盖度 C1/C2/C3** | 这个功能**验证到什么程度**？ | 决定**测试投入**与**物理观察期** |
| **范围 S1/S2/S3** | 这个功能**做多少**？ | 决定**开发投入** |

> 只报覆盖度不报范围 → 客户以为买的是"完整功能 + 高覆盖"，实际收到"缩水功能 + 高覆盖"→ 争议。
> 只报范围不报覆盖度 → 客户以为买的是"完整功能"，实际收到"功能做完了但没验证"→ 事故。
> **必须成对出现。**

### 6.1 覆盖度分级

| 档位 | 名称 | 用例覆盖 | 验证手段 | 物理观察期 | 适用 |
|---|---|---|---|---|---|
| **C1** | **冒烟级** | 主路径 + 关键边界（~10~20 条） | AI 生成单测 + 人工走查主流程 | 无 | 内部工具、低风险、展示型需求 |
| **C2** | **完整级** | 全量用例 + 回归（~40~80 条） | AI 生成 + 人工审阅 + 完整回归 + 接口契约测试 | 0.5~1 日 | **生产系统默认档** |
| **C3** | **生产就绪级** | C2 + 异常/极端场景 + 故障演练 | C2 全部 + 影子运行 + 灰度放量 + 回滚演练 + 监控接入 | 3~7 日 | **涉及实盘资金、策略引擎、订单状态机** |

### 6.2 范围分级

| 档位 | 名称 | 交付范围 | 典型形态 |
|---|---|---|---|
| **S1** | **核心版** | 只做**主链路可跑通**的那条线 | 单维度聚合、单图表、核心接口；无下钻、无导出、无历史回溯 |
| **S2** | **标准版** | 主链路 + 常规扩展 | 完整维度 + 下钻明细 + 筛选 + 权限控制 |
| **S3** | **完整版** | S2 + 高级能力 | + 历史回溯 + 导出 + 实时推送 + 告警 + 多端同步 |

### 6.3 档位与交付的绑定规则

- **涉及实盘资金/订单执行/策略信号** → **强制 C3**，不接受降档（安全底线）
- **涉及新数据通道或协议变更** → 至少 C2
- **纯展示、纯内部工具** → 可选 C1
- 档位一经确定，**验收标准即按该档位的用例清单执行**——这是防止"交付时扯皮"的关键契约

### 6.4 各档位的产出人天参考

| 需求规模 | C1 | C2 | C3 |
|---|---|---|---|
| 小型 | 0.2~0.4 | 0.5~0.8 | 1.0~2.0 |
| 中型 | 0.4~0.8 | 1.0~1.8 | 2.0~4.0 |
| 中大型 | 0.8~1.5 | 1.8~3.0 | 3.5~6.0 |
| 大型 | 1.5~3.0 | 3.0~5.0 | 6.0~10.0 |

> 注意：随需求规模上升，**C1 与 C3 的差距从 5x 收窄到 3x**——因为 C1 档省下的是验证投入，而验证投入在大型需求中的绝对占比本就不高。

### 6.5 三档交付套餐（推荐对外报价形态）

把**范围**与**覆盖度**绑定成三档，客户只需选一档：

| 套餐 | 范围 | 覆盖度 | 说明 | 适合 |
|---|---|---|---|---|
| **P1 快速上线** | S1 | C1 | 主链路可跑通，冒烟验证 | 先上线看效果、预算敏感、可快速迭代 |
| **P2 标准交付** ⭐ | S2 | C2 | 完整功能 + 完整回归 | **生产系统默认推荐** |
| **P3 生产就绪** | S3 | C3 | 全量功能 + 影子 + 灰度 + 演练 | 涉及实盘资金 / 策略引擎 |

> **升级路径**：客户常先选 P1 上线，验证有效后升级 P2/P3。
> **这是本框架最重要的商业设计**——把"客户不确定要多少"变成"客户可以先小步开始"，成交率远高于单点报价。
>
> **升级定价**：P1 → P2 升级时，已完成的开发部分**不重复收费**，只收"补做范围 + 覆盖度差额"（按 §8.3 变更规则）。
> 这让客户敢选 P1，也让 P1 成为一个**低门槛入口**而非"缩水陷阱"。

## 7. 报价模型

### 7.1 角色费率表（AI 时代修订版）

**关键变化：判断类角色单价 > 执行类角色单价。** 这反映真实价值来源（§1.4）。

| 角色 | 日费率区间（元/人天） | **示例取中值** | 相比 v1.0 | 计价依据 |
|---|---|---|---|---|
| **架构师 / 技术负责人** | **3,500~4,500** | **4,000** | ↑ 25% | 方案判断、架构决策、疑难攻坚、风险兜底 |
| **项目管理 / 需求分析** | 1,800~2,200 | **2,000** | ≈ | 沟通协调、验收组织 |
| **高级后端** | 2,400~3,000 | **2,700** | ↓ 10% | 编码工时价值下降 |
| **前端** | 2,000~2,600 | **2,300** | ↓ 10% | 同上 |
| **节点端 / 量化** | 2,400~3,000 | **2,700** | ↓ 5% | 交易逻辑判断仍有价值 |
| **桌面端** | 1,800~2,400 | **2,100** | ↓ 10% | |
| **QA / 测试** | 1,200~1,800 | **1,500** | ↑ 20% | **覆盖度是稀缺资源，需求上升** |
| **运维 / SRE** | 1,600~2,200 | **1,900** | ≈ | 部署、监控、故障处理 |
| **AI 工具摊销**（非人天） | 500~1,500 / 需求 | **800~1,000** | 新增 | Token/API + 工具许可（**不含人工监督，人工已计入 ②**） |

> **报价口径**：含社保、场地、工具、利润的外包价。非个人到手工资。

### 7.2 四段式成本模型（v2.1 修正：无重复计算）

> **v2.0 的两处错误**（已修正）：
> 1. **漏算**——测试执行工时（T12/T13，示例中 3.15 人天 QA）没有进入任何成本桶，导致报价与 L1 人天对不上。
> 2. **重复计算**——AI 产出人天既乘了角色日费率，又额外计了一份"监督摊销"。
>
> **修正原则**：**L1 的每一个人天，必须在成本模型里恰好出现一次。** 校验方法：把 ①②③ 三段的费率还原，合计应等于 L1 产出人天。

```
直接成本 = ① 判断投入 + ② 产出投入 + ③ 验证投入 + ④ 责任保障

① 判断投入 = Σ(T10 需求澄清, T11 用例设计, 架构决策, 验收定义) × 对应角色费率
     —— AI 压不动，成本刚性，但通常只占 20~25%

② 产出投入 = Σ(T1~T9, T15 产出人天) × 产出角色费率 + AI 工具摊销
     —— 编码、迁移、部署、缺陷修复、AI 生成用例

③ 验证投入 = Σ(T12, T13 产出人天) × QA / 节点端 / 运维费率
     —— 功能测试、回归、影子运行、灰度观察。**独立成段，不折进开发**

④ 责任保障 = 风险系数 × (① + ② + ③)
     —— 缺陷兜底、质保期、实盘风险。与代码量无关，与风险成正比

─────────────────────────────────────────────
管理分摊 = 直接成本 × 10%~15%
风险准备 = 直接成本 × 15%~30%（按置信度）
成本小计 = 直接成本 + 管理分摊 + 风险准备
未税报价 = 成本小计 ÷ (1 - 目标毛利率 25%~35%)
含税报价 = 未税报价 × 1.06
```

**④ 责任保障系数**：

| 风险等级 | 场景 | 保障系数 | 强制档位 |
|---|---|---|---|
| R1 低 | 内部工具、展示 | 0.15~0.20 | C1 可选 |
| R2 中 | 生产系统非资金功能 | 0.20~0.30 | C2 |
| R3 高 | 涉及实盘资金 | 0.30~0.50 | **C3 强制** |

> **小单注意**：管理分摊 + 风险准备 + 保障系数叠加后是 **1.7~2.1x** 放大。这意味着**单个小需求的报价里，固定管理成本占比很高**。§7.5 的价格地板与"合并打包"策略正是为此设计。

> **三条硬校验（每次报价前必做）**：
> 1. **无遗漏**：L1 的每个人天都能在 ①②③ 中找到归属。反查方法：把 ①②③ 的人天还原后合计，应与 L1 总人天吻合。
> 2. **无重复**：同一人天不得在两段中重复计价。检验方法：按角色汇总 ①②③ 的人天，与角色映射表逐行对照。
> 3. **单价回验**：含税报价 ÷ L1 人天，应落在 §7.1 费率区间的合理倍数内（经验值 4,500~7,000 元/人天）。
>    明显偏低 → 漏算；明显偏高 → 重复计算或毛利异常。
>
> **取整纪律**：**先取整到百元，再进入下一层计算**，避免"逐层四舍五入"导致表格加总对不上。
> 判定表中的每个任务产出人天保留 3 位小数，**小计按已取整的显示值求和**——这样读者手算也能对上。

### 7.3 报价单必须包含的 9 项

1. **报价总价**（未税 / 含税）—— 唯一有法律约束的数字
2. **报价区间**（P50 / P80）与区间成因
3. **三档交付套餐菜单（P1 / P2 / P3）**—— 每档同时锁定**范围**与**覆盖度**，让客户选，而不是你猜
4. WBS 产出人天表（按任务类型 + 压缩系数）
5. 物理工期排期表（带日历日期）
6. **交付物清单**（可验收的实体）
7. **覆盖度档位与用例清单口径**（C1/C2/C3 三选一）
8. **明确排除项**
9. 付款节点 + 验收标准 + 质保 + 变更流程

### 7.4 付款节点（按档位调整）

| 节点 | 比例 | 触发条件 |
|---|---|---|
| 签约预付款 | 30% | 合同签署、排期确认、档位选定 |
| 中期款 | 40% | 核心功能开发完成 **且提测通过**（开发完成 ≠ 中期款条件达成） |
| 验收款 | 30% | 全部交付物按**所选档位用例清单**验收通过，目标环境稳定运行 5 个工作日 |

> 建议加 **5%~10% 质保金**，验收后 30~90 天释放。
> **C3 档可增设 10% 影子运行尾款**——实盘观察期结束后支付。

### 7.5 价格地板与接单判断

**v1.0 缺失的关键机制。** AI 时代单个小需求的报价很容易低到不值得做。

```
最低接单价（含税）：8,000 ~ 15,000 元
```

**低于地板价时的处理顺序**：

1. **降低覆盖度档位**（C3 → C2 → C1）—— 让客户在"便宜"和"稳妥"之间做选择
2. **合并需求打包**——多个小需求合并到一次交付，摊薄沟通与部署成本
3. **提高客户侧参与度**——要求需求方提供 PRD、UI 稿、用例（**"半自助"模式**，这是 AI 时代最有效的降本杠杆）
4. **改按月订阅 / 迭代包**——把一次性利润转成持续收入
5. **拒绝**——如果以上都不成立

**应该拒绝的信号**：

| 信号 | 原因 |
|---|---|
| 需求含糊 + 预算极低 + 期望高质量 | 三者不可兼得，风险必然转嫁客户 |
| 说不清验收标准 | 交付时必然扯皮，争议成本 > 利润 |
| 要求在无实盘环境交付"实盘级"保证 | 物理上无法兑现，不要承诺 |
| 需求方拒绝书面确认 | 变更无约束，范围必然蔓延 |

### 7.6 排除项标准写法

明确写入排除项（否则等同于包干）：

- 第三方服务费用（行情源、短信、推送、服务器、证书、域名）
- 硬件采购与机房费用
- 超出约定范围的数据迁移、历史数据清洗
- 既有系统的历史缺陷修复
- 新增中间件引入的架构改造
- 需求变更导致的重构
- **覆盖度超出所选档位（C1/C2/C3）的测试与验证**——可按 §5.3 变更流程追加
- 长期运维、值班、7×24 支持（另签维护合同）
- 多语言 / 多币种 / 境外合规适配
- **AI 产出物的后续人工审计**（若客户要求逐行人工复核，需单独计价）

## 8. 风险、变更与质量保障

### 8.1 风险登记表

| 风险类别 | 典型风险 | 概率 | 影响 | 应对 |
|---|---|---|---|---|
| 需求风险 | 需求方无法及时确认待定项 | 中 | 工期 +1~3 日 | G1 闸口卡死不启动；确认后才计开发工时 |
| **AI 特有风险** | **AI 产出代码存在隐蔽缺陷、边界遗漏** | **高** | 覆盖度不足 → 实盘事故 | **强制 C2/C3 档**；AI 产出必过人工评审 + 用例验证 |
| **AI 特有风险** | **AI 生成的"看似正确"逻辑（幻觉）** | **中** | 隐蔽错误 | 关键路径（T14/T8）人工逐行复核，不信任 AI 自测结果 |
| 技术风险 | 触及 MT5 实盘订单状态机，改动不可回滚 | 高 | 3~8 人天 | 影子运行 + 灰度放量 + 分支保护 + 双人复核 |
| 依赖风险 | 依赖外部 API / 行情源 / 第三方服务 | 中 | 2~5 人天 | Mock 层先行；接口契约先行冻结 |
| 数据风险 | 历史数据迁移后对账不一致 | 中 | 3~6 人天 | 双写对账 + 灰度切流 |
| 环境风险 | MT5 终端 / 实盘账号不可用 | 中 | 2~4 人天 | 提前锁定测试窗口；`MockMT5Client` 兜底 |
| 人员风险 | 关键角色（量化 / 节点端）单点 | 中 | 2~5 人天 | 关键模块双人熟悉；文档同步 |
| 进度风险 | 物理下限被压缩，导致承诺失守 | **高** | 工期 | **按 §5 下限排期，不因 AI 快而缩短承诺** |

### 8.2 估算置信度 → 区间与风险系数

| 置信度 | 判定标准 | 报价区间 | 风险准备系数 | 强制档位 |
|---|---|---|---|---|
| **高** | 成熟 PRD + 方案已评审 + 有可类比历史实现 + 复用度 >70% | P50 ± 8% | 15% | 可选 C1 |
| **中** | 描述清晰但缺原型；有类比实现；待定项 ≤ 2 | P50 ± 15% | 20% | C2 |
| **低** | 一句话需求；涉及新架构；待定项 > 3 | P50 ± 30% | 25% | C3，且**先做付费的需求细化** |

> **规则**：置信度"低"时**不出固定总价**，改出"预估区间 + 付费的需求细化阶段"。把不确定性转化为确定合同。

### 8.3 变更管理流程

```
变更提出 → 影响分析(产出人天/工期/费用) → 书面确认 → 变更单 → 排期更新
```

**变更计价规则**（基于产出人天，而非传统人天）：

| 增量产出人天 | 处理 |
|---|---|
| < 0.2 | PM 审批，直接计入，不额外收费（服务诚意） |
| 0.2~1.0 | 签补充协议，工期顺延 |
| > 1.0 | 重新走完整评估流程 |

### 8.4 阶段 DoD

| 阶段 | 完成标准 |
|---|---|
| 需求沟通完成 | 澄清纪要书面确认；待定项**全部关闭**；验收标准成文；**覆盖度档位选定** |
| 开发完成 | 代码合入主干；单测通过；**人工代码评审通过（AI 产出必审）**；无 P0/P1 遗留缺陷；部署脚本可跑通 |
| 测试完成 | 按所选档位用例清单**全量执行**；无 P0/P1 缺陷；P2 有明确排期；回归通过 |
| 验收完成 | 交付物签收；目标环境稳定运行 5 个工作日；文档交付 |

### 8.5 AI 辅助开发的额外 DoD 要求

这是 v2.0 新增的、**AI 项目特有的验收项**：

- [ ] **AI 产出代码经人工逐行评审**，重点检查：业务边界、空值/异常路径、并发安全、金额/精度处理
- [ ] **关键路径（T14 实盘资金逻辑）双人复核**
- [ ] **不采信 AI 自测结果**——AI 生成的测试只能证明"代码按 AI 的理解工作"，边界场景必须由人定义
- [ ] **文档与代码一致性检查**（AI 生成的文档常与实现漂移）
- [ ] **依赖与许可证检查**（AI 可能引入未经审查的第三方库）
- [ ] **灰度开关 + 回滚路径**已就位并演练过

## 12. 常见反模式与纠正

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| **用传统人天费率估 AI 项目** | **高估 5~9 倍，直接失去市场** | **§4 压缩系数 + §7 四段式成本** |
| **把产出人天直接当工期** | 承诺日期失守 | **§5 物理下限校验** |
| **把压缩系数乘到测试覆盖度上** | 覆盖度不足 → 实盘事故 | **T11/T12/T13 系数保持 1.0** |
| 需求还没定就开始估工期 | 估算必然被推翻 | 需求澄清独立阶段 + G1 闸口 |
| 一句话报价，无档位 | 客户无法选择，争议无解 | **三档菜单（C1/C2/C3）** |
| 不写排除项 | 隐性需求全算在合同里 | 排除项逐条列明 |
